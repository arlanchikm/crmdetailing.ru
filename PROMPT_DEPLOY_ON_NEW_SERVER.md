# Промпт: развернуть CRM Detailing на новом VPS

Скопируйте текст ниже в Codex вместе с архивом `crm-detailing-20261010.tar.gz`.

```text
Ты — мой DevOps-инженер. Нужно перенести CRM Detailing из приложенного архива на НОВЫЙ чистый VPS и подготовить переключение сайта.

Работай по содержимому архива и README.md, не угадывай команды и не считай старые инструкции актуальными, пока не проверишь их против файлов проекта. Целевой сервер — Ubuntu 24.04 LTS, Docker Compose. Проект Django, PostgreSQL, Redis, Celery и Caddy; основной домен — crmdetailing.ru, адреса компаний — поддомены.

Порядок работы:
1. Проверь SHA256 архива, его состав, Dockerfile, compose.prod.yaml, deploy/Caddyfile и .env.production.example. Не выводи секретные значения в чат и не помещай их в командную строку, историю shell или журналы.
2. Сначала подготовь новый VPS, не трогая действующий сервер: обнови пакеты, настрой SSH-ключ, пользователя для администрирования, firewall (SSH, TCP 80/443; UDP 443 для HTTP/3), установи Docker Engine и Compose plugin. Не отключай текущий способ SSH-входа, пока не проверен вход в новой сессии.
3. Загрузи архив в /opt/crm-detailing, проверь checksum, распакуй его и выставь владельца/права. Не запускай `docker compose down -v`, не удаляй volumes и не выполняй команды, которые могут уничтожить действующие данные.
4. Создай `/opt/crm-detailing/.env.production` из `.env.production.example`, права 600. Секреты вводи только через защищённый интерактивный ввод на сервере или секрет-хранилище. Сохрани совместимость с текущей базой: используй актуальный production `.env.production` из резервной копии, если он есть; не генерируй заново DJANGO_SECRET_KEY и PostgreSQL пароль без причины.
5. ДО первого запуска приложения найди самый свежий успешный restic snapshot на прежнем сервере/во внешнем хранилище. Бэкап содержит `.env.production`, дамп PostgreSQL и архив media. Получи значения доступа к backend и пароль restic из защищённой конфигурации старого сервера. Не отправляй их в чат. Не создавай новый пустой restic repository поверх старого. Восстанови выбранный snapshot во временный каталог, проверь целостность дампа и media и только затем восстанови БД и медиа на новом VPS. Если актуальная копия недоступна, остановись и объясни, что именно нужно получить; не создавай пустую рабочую CRM вместо восстановления.
6. Сверь доменные параметры в `.env.production`: APP_DOMAIN и DJANGO_PRIMARY_DOMAIN — crmdetailing.ru; проверь allowed hosts, CSRF origins и suffixes для поддоменов. Проверь SMTP `smtp.yandex.ru:465` (SSL), отправителя `no-reply.crmdetailing@yandex.ru` и поддержку `info.crmdetailing@yandex.ru`. YooKassa оставь в безопасном test mode, если боевые параметры не предоставлены отдельно.
7. До запуска проверь, что у нового VPS есть свободные TCP 80/443 и UDP 443, а DNS-провайдер позволит направить `@`, `www` и `*` на новый IPv4. Не переключай публичные DNS-записи и не выключай старый VPS без моего отдельного подтверждения.
8. Подними compose.prod.yaml, проверь миграции, collectstatic, здоровье web/db/redis, один Celery worker с beat, Caddy, журналы ошибок и `/health/`. Проверь главную страницу, вход и поддомены с восстановленной базой. Не создавай фиктивные компании и платежи в production.
9. Подготовь короткий отчёт: адрес нового VPS, что восстановлено, какие сервисы healthy, результаты проверок, какие секреты/настройки ещё нужны, DNS-изменения для переключения и план отката на прежний сервер. Остановись перед DNS cutover и дождись моего подтверждения.

Секреты, пароли, приватные ключи и дампы с данными клиентов не публикуй в ответах и не загружай в сторонние сервисы. Любую необратимую операцию сначала объясни и запроси подтверждение.
```
